Rendered AFTER the list of files on every review surface: an operator arriving from an alert must reach the first file without scrolling past instructions. `root` (optional) names the collection root for the restore steps; `copy_note` (optional) is the truncated-copy-list notice. Two claims are never made here (spec: "Issues are resolved by actions named for their outcome"): that accepting a change can be undone by a rescan, and that accepting a deletion deletes a proof. And the promise about a changed file is exact: it clears itself only when put back exactly as it was before the change — the scan compares against the digest it kept. #}
{{ m.icon("checkCircle", size=15, stroke=1.9) }} What the actions do
Accept change
This is the file now. Cairn recorded the new contents when it found the change; accepting clears the issue, and this change is not reported again. Until you accept, Cairn keeps the fingerprint the file had before; once you accept, it is gone.
Accept deletion
Cairn forgets the file: its record, its first-seen date and the link to its timestamp proof are removed. Nothing on disk is deleted and the proof file stays in the proof store, but the file is no longer listed under Verify.
Stop flagging this…
For a file that changes as part of normal work. It opens a page that proposes a rule — this file, its folder, or every file of that name — and shows what each would match. From the next scan, ordinary changes to matching files are recorded but not flagged. A rule accepts nothing already listed, and never covers a deletion, possible corruption or an unusually large change.
{{ m.icon("download", size=15, stroke=1.9) }} To get files back instead
Cairn watches your files read-only — it never restores them itself. {% if copy_control|default(true) %}Copy the affected paths with Copy paths,{% else %}Open the collection's own review page to copy the affected paths,{% endif %} restore them with your own backup tool (restic, Borg, rsync, Time Machine, a cloud sync…), then run Scan now on the collection.
  • A missing file that comes back is re-read and compared against the fingerprint recorded before it went missing. If it matches, the missing alert closes by itself (a file that also had an unaccepted change stays listed as changed). If it does not — the wrong snapshot, a truncated restore — the missing alert is closed and replaced by a new came back different issue for you to check.
  • A changed file closes its own issue too — but only if it is put back exactly as it was before the change (Cairn keeps that fingerprint until you accept). Any other version shows up as one more change.
  • For files you don't want back, use Accept deletion.

How to recover (any backup tool)
  1. Copy the affected paths with the Copy paths button (relative to the collection root) or Copy full paths.
  2. In your backup tool, restore exactly those paths to the collection root {{ root }}.
  3. Run Scan now on the collection page. A missing file that reappeared with the recorded contents returns to healthy; one whose contents differ is flagged came back different — check that one before you trust it.
  4. For anything you don't want back, use Accept deletion — for a folder, or one file at a time from its row.
